# FieldFlow

**Планирование выездных работ и перепланирование в течение дня.** FieldFlow помогает диспетчеру распределять заявки между инженерами с учётом времени, адресов, навыков, оборудования и транспорта. Проект создан для кейса «Билайн Бизнес» хакатона «Лидеры цифровой трансформации».

**[Открыть работающий сайт](https://fieldflow-web-zc7t.onrender.com/)** · [Исходный код](https://github.com/ddgg127/Imoscow)

> Сайт размещён на бесплатном тарифе Render. После простоя первое открытие может занять около минуты. Для знакомства не нужны учётная запись и свои данные: в интерфейсе есть готовый демонстрационный набор.

## Какую задачу решаем

У диспетчера есть заявки с адресами, временными окнами и требованиями к исполнителю. У инженеров различаются смены, навыки, транспорт и выданное до начала дня оборудование. Ручное распределение такого потока занимает время; отмена заявки, срочная работа или уход инженера требуют пересмотра оставшейся части плана.

FieldFlow строит расписание и показывает его на карте. Заявки повышенного приоритета учитываются прежде обычных. Если выполнить заявку при заданных ограничениях нельзя, сервис оставляет её без назначения и показывает причину. Диспетчер видит результат, а инженер — свою смену, задания и маршрут.

## Попробовать за 3 минуты

1. Откройте [сайт](https://fieldflow-web-zc7t.onrender.com/) и во вкладке **«Генератор»** нажмите **«Пример 12 / 51»**.
2. Нажмите **«Рассчитать маршруты»**. Расчёт может занять десятки секунд; повторный запуск на это время блокируется.
3. Во вкладке **«Планирование»** выберите инженера, чтобы увидеть его маршрут и задания. Кнопка **«Все маршруты»** вернёт общую картину.
4. Переместите **«Время просмотра»**, чтобы увидеть план в другой момент смены. Откройте заявку или перейдите в окно инженера через переключатель внизу бокового меню.
5. Откройте **«Аналитику»**: там показаны назначения, загрузка и сравнение с базовым способом распределения.

В примере одна заявка специально требует отсутствующий вид транспорта. Она должна остаться без исполнителя: это демонстрация того, что ограничения не обходятся ради красивой цифры покрытия.

## Что умеет сервис

| Возможность | Что видит пользователь |
| --- | --- |
| Первичное планирование | Расписание инженеров, назначенные и неназначенные заявки, карту маршрутов и временную шкалу |
| Ограничения | Учёт навыков, оборудования, транспорта, смены и временного окна каждой заявки |
| Изменения в течение дня | События с заданным временем: новая или срочная заявка, отмена, изменение заявки, недоступность инженера |
| Работа диспетчера и инженера | Поиск и фильтры, карточки заявок, отдельное окно инженера, сообщение о выходе из смены или ЧС |
| Объяснение результата | Причины неназначения, журнал уведомлений, изменения после перепланирования и аналитика |
| Данные | Генерация и редактирование набора, импорт CSV/JSON, выгрузка плана в CSV/JSON |

После события прошедшие и уже выполняемые работы сохраняются, а оставшаяся часть дня пересчитывается. Если инженер уходит во время выполнения заявки, сначала завершается текущая работа; будущие задания передаются на перепланирование. Сценарий и рассчитанный план сохраняются в этом браузере после перезагрузки. Синхронизации между устройствами и общего серверного хранилища пока нет.

## Как получается план

```text
Заявки + инженеры + ограничения
              ↓
Дорожное время и расстояние
              ↓
OR-Tools: распределение и порядок работ
              ↓
Карта, расписание, причины и аналитика
```

Алгоритм оптимизации использует **OR-Tools** для задачи маршрутизации с временными окнами. Сначала он стремится назначить больше заявок повышенного приоритета, затем увеличить общее число назначений. При одинаковом покрытии совместно учитываются пробег, количество задействованных инженеров, межзонные выезды, а при перепланировании — смена исполнителя и сдвиг обещанного времени. Это взвешенная сумма штрафов, а не строгий приоритет стабильности перед пробегом. Поиск ограничен по времени; математический оптимум не гарантируется. Оборудование закрепляется за инженером до начала смены и в течение дня не меняется.

В карточке заявки раздел «Почему именно этот инженер» показывает обязательные ресурсы, прибытие, начало и окончание работы, соседние остановки и зону. Для исходного плана при доступной матрице можно раскрыть локальное сравнение с тремя ближайшими по стартовой точке кандидатами. Такая проверка вставки не доказывает превосходство назначения над всеми возможными планами; после событий она скрыта. Отмена и вставка обычной заявки могут обрабатываться локально без повторного запуска OR-Tools — способ изменения указан в уведомлении плана.

В аналитике план сравнивается с **базовым последовательным способом**: заявки идут во входном порядке, каждая назначается первому подходящему инженеру и добавляется в конец его маршрута. Это отдельный расчёт на тех же входных данных, а не «пробег из прошлого». Процент изменения пробега вычисляется по заявкам, которые есть в обоих планах, и показывается только при достаточном качестве дорожных данных. Покрытие всех заявок отображается отдельно.

## Данные и ограничения демо

- Пример 12/51 и исходный набор 205 заявок используют **синтетические данные**. Демонстрационные инженеры и часть нормативов — допущения модели, а не реальные сотрудники и фактические назначения «Билайн Бизнес».
- Дорожные линии на карте и время поездки для расчёта имеют разные источники. Если дорожная матрица недоступна, план помечается как **оценочный**; такой расчёт нельзя использовать как доказательство точной экономии пробега.
- Публичные картографические и геокодирующие сервисы могут отвечать медленно или быть недоступны. Для производственного внедрения нужны контролируемый источник дорожных данных, подтверждённые нормативы и интеграция с учётными системами.
- Статусы выполнения и положение инженера на шкале времени в демо выводятся из **плана**, а не из реальной геолокации. Пользовательские данные в открытый демонстрационный сайт загружать не следует.

## Локальный запуск

Понадобятся **Node.js 22.19+** и **Python 3.12+**. Команды ниже подходят для PowerShell в Windows:

```powershell
npm ci
python -m venv .venv
.venv\Scripts\python -m pip install -r solver_service\requirements.txt
.venv\Scripts\python -m uvicorn solver_service.app:app --host 127.0.0.1 --port 8008
```

Во втором терминале:

```powershell
$env:SOLVER_URL = "http://127.0.0.1:8008"
npm run dev
```

Откройте адрес, который выведет сервер разработки. Без работающего Python-сервиса расчёт маршрутов не запускается: скрытой замены OR-Tools упрощённым алгоритмом нет.
