## Проверка загрузки Марии Козловой — 28 сентября 2026

В генераторе 12/51, seed 42, окна в среднем 240 минут заявки №0012 и №0015 совпадали с навыком и аварийным комплектом Марии, но были в «Югоцентре», а Мария — в «Юго-востоке». Жёсткий фильтр зоны запрещал оба назначения. №0018 дополнительно требует автомобиль, поэтому велосипед Марии остаётся недопустимым транспортом для неё.

Изменения: зона стала предпочтением в OR-Tools, а не запретом; навык, комплект, транспорт, смена и окно остаются обязательными. До смены подбор комплектов учитывает межзонную работу и обмен комплектами между инженерами разных зон. Во время смены перевыдача не разрешается. Карта сохраняет все остановки показанного инженера при фильтрации по зоне; сводка зон считает заявки по зоне адреса, а не базе инженера.

## Исправленные дефекты

1. Генератор выдавал случайное число срочных и транспортно ограниченных заявок вместо значения в настройках. Теперь доли превращаются в точные целые количества; при 15/100 это 15 и 25.
2. Средняя длина окна не совпадала с настройкой (фактически 260 вместо 240 минут). Теперь среднее точно 240 минут, окна остаются разными.
3. В генераторе был внутренний числовой приоритет `10` при двух уровнях ТЗ. Теперь `1/2` во всех новых данных и CSV; отображение и выбор обычной заявки для отмены используют общий классификатор приоритета.
4. Из 15 стартовых точек 14 попадали в одну зону, в «Юго-восток» — ни одной. Генератор распределяет инженеров по зонам, даёт каждой используемой зоне квалифицированного инженера и выбирает транспортное ограничение среди местных подходящих исполнителей.
5. Во время первого расчёта все заявки ошибочно показывались как «не удаётся назначить». Пока расчёт не завершён, они показываются ожидающими.
6. После объединения веток из планирования исчезло управление временем события. Оно восстановлено. Эксперимент с изменением окон был добавлен позднее, а затем удалён по запросу пользователя; исходные окна набора теперь не изменяются в планировании.
7. Форма новой заявки использовала названия навыков исходного CSV даже при работе с набором по ТЗ. Теперь варианты берутся из текущего состава инженеров, а созданная заявка получает совпадающий навык и оборудование.
8. Встроенный граф не покрывал часть северных московских адресов генератора. Он расширен из хранящихся в проекте OSM-выгрузок и объединён с прежним графом удалённых точек. При невозможности проезда по выбранному направлению строится явно обозначенный оценочный путь по другому дорожному профилю, без прямой пунктирной линии.
9. Исправлены неточные внутренние описания приоритетов и обязательности оборудования в документации.
10. Поле времени события визуально принимало новое значение, но при следующем действии возвращалось к 13:10. Ввод теперь синхронизируется с состоянием приложения сразу.
11. Отмена заявки, которой не было в рабочем маршруте, могла вызвать десятки ненужных перестановок, если baseline её назначал. В этом случае текущие маршруты теперь сохраняются, а метрики пересчитываются без запуска solver.
12. Отменённая заявка учитывалась в фильтре «Не удаётся назначить». Добавлен отдельный статус и фильтр «Отменены».

## Оставшиеся ограничения и рекомендации

### Проверка обработки HTTP 429 (28 сентября)

Удалены фоновые принудительные расчёты при открытии карточки: их результаты не использовались интерфейсом. В прокси добавлены проверка готовности сервиса, очередь с приоритетом планирования, объединение одинаковых запросов и до пяти попыток при временных HTTP 429/502/503/504. `Retry-After` соблюдается, общий срок ожидания ограничен 180 секундами. Недоступный сервис не заменяется эвристикой, прежний план сохраняется. Python выполняет один поиск одновременно; health-check не блокируется тяжёлым расчётом.

Проверки: 119 JS-тестов, 26 Python-тестов, typecheck, lint (без ошибок) и производственная Node-сборка прошли. В интеграционном прогоне производственного сайта намеренно возвращались HTML-ответ 429 при первом health-check и два ответа 429 при расчёте. Два одновременных одинаковых запроса оба завершились HTTP 200, OR-Tools назначил 50/51 заявки; реальный поиск выполнялся один раз. Постоянный 429, неверные данные 422, отмена запроса, освобождение очереди после тайм-аута и неподтверждённый движок проверены отдельно. При одиночных запросах к прежней публичной версии постоянный 429 не воспроизвёлся; это ограничение диагностики, а не доказательство отсутствия ошибки у других пользователей.

Позднее ошибка внешнего сервиса была получена и на публичном health-check: вместо JSON пришёл текст `Too Many Requests`, который прежний прокси не мог разобрать. Поэтому подготовлено размещение сайта и OR-Tools в одном Docker-контейнере с соединением через `127.0.0.1`, исключающим этот публичный переход. Локальный запуск двух процессов, health-check, два одновременных одинаковых запроса 3/3 и полный сценарий 50/51 прошли. Linux-контейнер с 512 МБ проверяется отдельным CI-заданием; статус публикации нужно подтверждать по SHA поля `deployment` в публичном `/api/solver`.

### Ограничения эксплуатации

- **Точные дорожные метрики.** Публичные OSRM/Valhalla в этой среде отвечали ошибками, поэтому матрица solver оценочная, хотя линии на карте построены по дорогам. Для демонстрации с доказуемой экономией развернуть собственный маршрутизатор или подготовить заранее рассчитанную матрицу для фиксированного набора.
- **Общественный транспорт.** При отсутствии мультимодального маршрутизатора показывается подписанный пешеходный путь; реальное расписание транспорта не учитывается. Нужен отдельный источник графа и расписаний, если этот режим будет важен для оценки.
- **География и хранение.** Локальный граф покрывает встроенные сценарии; произвольный импорт за его пределами зависит от внешнего маршрутизатора. Сценарии и ручные изменения не сохраняются после перезагрузки страницы. Для эксплуатации нужны расширение зоны обслуживания и сохранение данных.
- **Стартовые точки.** PDF требует точку старта, но не требует офисов. Генератор использует реальные адреса зданий как старты, а не модель складов/выдачи оборудования. Если нужна организационная модель офисов, следует завести справочник офисов, запасов и закрепления инженеров.
- **Приоритет.** PDF требует более высокий приоритет срочной заявки при перепланировании; пользователь отдельно потребовал ставить все выполнимые повышенные заявки выше общего покрытия. Solver применяет именно это правило. Если повышенные заявки физически несовместимы по навыку, ресурсу или времени, интерфейс показывает их номера и причины, а не обещает невозможное назначение.
